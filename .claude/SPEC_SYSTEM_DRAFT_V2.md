# Specification System - Draft Proposal v2

**Purpose:** Empower AI coding assistants to write comprehensive, complete specifications before implementation.

**Changes from v1:** Incorporated critique feedback - replaced scoring with Pass/Fail gates, added missing domains, refined workflow.

---

## Core Design Principles

1. **No False Rigor** - A spec is either actionable or it isn't. No vanity metrics.
2. **Blockers vs Warnings** - Critical issues halt progress; minor issues get flagged.
3. **LLM-based Critique** - Context-aware validation, not brittle keyword matching.
4. **Explicit Unknowns** - What we don't know is as important as what we do know.
5. **Critic-Refiner Loop** - Iterate until blockers = 0.

---

## Specification Format (YAML)

```yaml
spec_meta:
  id: SPEC-001
  title: User Authentication Service
  version: 1.0
  status: DRAFT  # DRAFT | REVIEW | APPROVED | BLOCKED
  created: 2025-12-16
  last_validated: null

# WHY - Business context
objective: >
  Enable users to securely authenticate to the system using email/password,
  supporting session management and secure credential storage.

# DEFINITIONS - Prevent ambiguity
terms:
  - term: "Active Session"
    definition: "A JWT token that has not expired and has not been revoked."
  - term: "Failed Login Attempt"
    definition: "An authentication request with invalid credentials."

# REQUIREMENTS - The "Shall" statements
requirements:
  - id: REQ-001
    statement: "The system shall accept email and password as login credentials."
    type: FUNCTIONAL
    priority: P0
    acceptance_criteria:
      - "Given valid credentials, return 200 with JWT token."
      - "Given invalid credentials, return 401 Unauthorized."
      - "Given malformed request, return 400 Bad Request."
    edge_cases:
      - input: "Empty email"
        expected: "400 Bad Request with error 'email_required'"
      - input: "Empty password"
        expected: "400 Bad Request with error 'password_required'"
      - input: "Email > 255 chars"
        expected: "400 Bad Request with error 'email_too_long'"
    traces_to: [STORY-001]

  - id: REQ-002
    statement: "The system shall hash passwords using bcrypt with cost factor 12."
    type: SECURITY
    priority: P0
    rationale: "OWASP recommendation for password storage."
    acceptance_criteria:
      - "Stored passwords are bcrypt hashes, not plaintext."
      - "Hash verification succeeds for correct password."
      - "Hash verification fails for incorrect password."
    traces_to: [REQ-001]

  - id: REQ-003
    statement: "The system shall log all authentication attempts."
    type: OBSERVABILITY
    priority: P1
    acceptance_criteria:
      - "Successful logins logged with user_id, timestamp, IP."
      - "Failed logins logged with attempted_email, timestamp, IP, failure_reason."
      - "Logs do not contain passwords or tokens."
    traces_to: [REQ-001]

  - id: REQ-004
    statement: "The system shall return authentication response within 500ms at p99."
    type: PERFORMANCE
    priority: P1
    acceptance_criteria:
      - "Under normal load, p99 latency < 500ms."
      - "Under 10x load, p99 latency < 2000ms."
    constraints:
      - "Measured excluding network latency."

# DECISIONS - Choices made with rationale
decisions:
  - id: DEC-001
    question: "Session storage mechanism?"
    chosen: "JWT tokens (stateless)"
    alternatives:
      - option: "Server-side sessions"
        rejected_because: "Requires shared session store, complicates horizontal scaling."
      - option: "OAuth-only"
        rejected_because: "Adds external dependency, overkill for internal auth."
    rationale: "Stateless tokens enable horizontal scaling without shared state."

  - id: DEC-002
    question: "Password hashing algorithm?"
    chosen: "bcrypt with cost 12"
    alternatives:
      - option: "Argon2id"
        rejected_because: "Less widely supported in target runtime."
      - option: "PBKDF2"
        rejected_because: "Lower security margin than bcrypt at equivalent cost."
    rationale: "Industry standard, well-supported, tunable cost factor."

# CONSTRAINTS - Non-negotiable boundaries
constraints:
  - "Must integrate with existing PostgreSQL database."
  - "Must not introduce new external service dependencies."
  - "Must comply with GDPR data handling requirements."

# UNKNOWNS - Blockers that must be resolved
unknowns:
  - id: UNK-001
    question: "What is the password reset flow?"
    impact: "Cannot implement forgot-password endpoint."
    status: OPEN  # OPEN | RESOLVED
    resolution: null
    assignee: "User"

  - id: UNK-002
    question: "Should we support MFA in v1?"
    impact: "Affects authentication flow complexity."
    status: OPEN
    resolution: null
    assignee: "User"

# VALIDATION - Generated by Critic Agent
validation:
  timestamp: 2025-12-16T12:00:00Z
  status: BLOCKED  # PASS | BLOCKED
  blockers:
    - "UNK-001 is unresolved - cannot proceed with implementation."
    - "UNK-002 is unresolved - affects core flow."
  warnings:
    - "REQ-004 missing edge_cases section."
    - "DEC-001 rationale could be more detailed."
  coverage:
    functional: 1  # count of FUNCTIONAL requirements
    security: 1
    performance: 1
    observability: 1
    error_handling: 0  # WARNING: No error handling requirements
```

## Completeness Domains

The spec must address ALL of these domains (or explicitly mark as N/A with rationale):

| Domain | What It Covers | Example Requirements |
|--------|----------------|---------------------|
| **Functional** | What the system does | "Shall accept email/password" |
| **Security** | AuthZ, AuthN, data protection | "Shall hash passwords with bcrypt" |
| **Performance** | Latency, throughput, capacity | "Shall respond within 500ms p99" |
| **Observability** | Logging, metrics, tracing | "Shall log all auth attempts" |
| **Error Handling** | Failure modes, recovery | "Shall retry database connection 3x" |
| **Data** | Storage, retention, migration | "Shall store user data for 7 years" |
| **Integration** | External systems, APIs | "Shall call OAuth provider for SSO" |

## Validation Rules

### Blockers (Implementation Cannot Proceed)

1. **Unresolved Unknowns** - Any item in `unknowns` with status: OPEN
2. **Missing Acceptance Criteria** - Any requirement without testable criteria
3. **Undefined Terms** - Requirement uses term not in `terms` glossary
4. **Missing Domain Coverage** - No requirements for Security or Error Handling without explicit N/A

### Warnings (Should Fix, Won't Block)

1. **Passive Voice** - "Data is validated" instead of "System shall validate data"
2. **Compound Requirements** - Contains "and" or "or" linking distinct actions
3. **Missing Rationale** - Decision without explanation
4. **Missing Edge Cases** - Requirement without edge_cases section
5. **Weak Words** - Contains "fast", "user-friendly", "approximately" (flagged for review, not auto-blocked because context matters)

## Workflow: Critic-Refiner Loop

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  1. USER provides task description                          │
│                         │                                   │
│                         ▼                                   │
│  2. DRAFTER AGENT creates initial YAML spec                 │
│     - Asks clarifying questions first                       │
│     - Drafts requirements, decisions, constraints           │
│     - Lists unknowns explicitly                             │
│                         │                                   │
│                         ▼                                   │
│  3. CRITIC AGENT reviews spec                               │
│     - Checks all domains covered                            │
│     - Validates INCOSE compliance                           │
│     - Identifies blockers and warnings                      │
│     - Does NOT give numeric score                           │
│                         │                                   │
│                         ▼                                   │
│            ┌───────────────────────┐                        │
│            │ blockers.length > 0 ? │                        │
│            └───────────────────────┘                        │
│                  │           │                              │
│                 YES          NO                             │
│                  │           │                              │
│                  ▼           ▼                              │
│  4. REFINER AGENT      5. USER REVIEW                       │
│     fixes blockers        - Reviews spec                    │
│     (loop to step 3)      - Resolves unknowns               │
│                           - Approves or requests changes    │
│                                    │                        │
│                                    ▼                        │
│                         6. IMPLEMENTATION                   │
│                            - Code traces to REQ-IDs         │
│                            - Tests verify acceptance        │
│                            - No code without spec           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Implementation Approach

### Phase 1: Minimal Viable System
- YAML schema definition
- Simple validator (check required fields exist)
- Integration with existing [SPEC] mode workflow

### Phase 2: Critic Agent
- LLM-based review (not keyword matching)
- Domain coverage checking
- Blocker/warning classification

### Phase 3: Tooling
- `spec init` - Create new spec from template
- `spec validate` - Run critic, report blockers/warnings
- `spec status` - Show coverage and unknowns
- `spec export` - Generate markdown documentation

---

## What This Achieves

1. **Completeness** - Domain checklist ensures nothing forgotten
2. **Clarity** - Unknowns surfaced, not hidden
3. **Quality** - LLM critique catches ambiguity in context
4. **Traceability** - Requirements link to stories and to each other
5. **Actionability** - Blockers halt progress; spec is either ready or not
6. **Scalability** - Simple tasks need few requirements; complex tasks get full structure
